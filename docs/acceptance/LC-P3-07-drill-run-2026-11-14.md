## 4. The installed-build drill (outside the process, on the packaged build)

Driven by `E:\labcairn-local\lc-p3-07\installed-drill.py` against the frozen
exe (`win-unpacked\resources\backend\labcairn\labcairn.exe`,
`PYDANTIC_DISABLE_PLUGINS=1`, workspace beside the package as
`shell-env.template.json` names it). Raw observations, one JSON line each,
were printed by the run and are consolidated in
`installed-drill-evidence.json`:

- **interrupted write:** a mid-run `taskkill /F` of the CLI during the
  report/ingest window leaves the original byte-identical and the ledger
  without a half state. The kill-window drill proper ran in-process (§3),
  because the frozen exe does not honour `PYTHONPATH` `sitecustomize`
  (PyInstaller's embedded import supersedes it — probed and recorded).
- **locked source:** with a no-share hold on the original, `sources ingest`
  reports `failures=[original.bin, PermissionError Errno 13]`, `readable=0`,
  exit 0; the task still binds the source id; after release the same command
  reads and binds normally.
- **network loss:** `doctor --json` reports `providers: []` with no
  credential configured — no route, no spend, typed at the gate.
- **model timeout:** substitute-first per §12 §5.3; the installed build's
  operator surface is `task status`. The real-model row remains the named
  gap of §14 item 7.
- **known errors:** `sources inspect` resolves source *ids*, so escape
  spellings and absent names land as `source_not_found` (exit 3); a
  malformed task id lands as `invalid_arguments` ("task ids are UUIDv7").
  The refusal names and exit codes are the operator-visible vocabulary the
  manual's §3 rows quote.

## 5. Defect filed, not fixed

**D-07-01 — the frozen build refuses every `.txt` material.** On the
packaged build, `task create` over a `.txt` material refuses
`material_incomplete`, every file failing with
`ExtractionVersionError: cannot read
...\_internal\labcairn\material\text.py ... [Errno 2] No such file or
directory`. Mechanism: `src/labcairn/material/version.py`'s
`_module_source` reads each adapter module's `__file__` bytes from disk —
deliberately, so a version cannot silently stop tracking its code — but the
PyInstaller freeze embeds the pure-Python product modules inside
`labcairn.exe`, so `__file__` names a path under `_internal` that does not
exist. `.bin`/`other`-kind files are unaffected (no adapter version is
derived), which is why the earlier `.bin` workspaces bound normally and the
defect stayed hidden until the drill drove a `.txt` corpus.

**Owner:** `LC-P3-05` (frozen-backend packaging). The drill's boundary
(§12 §5.2) keeps 07 from repairing it; the witness suite's text-material
drills ran against the venv tree, where the source files exist, so the
witnesses' verdicts are about the property, not about this packaging defect.

## 6. The interrupted-write kill runs, honestly

Two full announce-then-kill runs were made. The first (basetemp
`E:\labcairn-local\tmp\p307b`) failed on its own temp-file assertion: the
kill left a 74-byte `.lc-write-*.tmp` with content, and the test had
asserted no temp with content survives. A probe pair
(`E:\labcairn-local\tmp\p307-probe\parent.py`, child blocked inside vs.
outside the open handle) showed the difference is **where the child sleeps
when killed**: a hard kill with the handle open keeps the file; with the
handle closed it does not. The product's contract — the *destination* is
never half-written, and cleanup removes only the temp its own call created
on the exception path — holds; the assertion was rewritten to check the
destination (never empty, never partial) and the ledger (`ATTEMPTING`
present, no `confirmed`/`failed` completion), and the temp-file fact moved
to the known-limits record. The corrected run (basetemp `p307b2`) passed
two of three; the third (`after_replace`) had armed its sentinel on the
*copy's* `Path.replace` — the patch is global, and the copy's replace fires
first — so the kill landed in the copy's window, not the publication's. The
window now keys on the replace target's name (`published.bin`), and the
corrected case passed in 2.79 s (basetemp `p307b3`), followed by the full
three-case run (basetemp `p307b4`). This is the drill discipline working:
the first red was the assertion overreaching the contract, the second was
the harness aiming at the wrong window, and neither was the product failing.

**The obligation that stays open.** The six files' per-file costs are
placeholder `0.0` entries, because **the costs must come from a runner**
(CLAUDE.md: "the numbers must come from a runner"; a development machine
gives a different answer and a different order). Until
`python .github/remeasure_shards.py <run-id>` re-apportions the partition
from a CI run's `--durations=0` log, the balance check runs on costs that do
not yet describe the new files — the same state the standing rule for a new
 test file describes (its cost may be apportioned from an existing run's
 log; a fresh push is not required). The
batch's single CI run, when the owner spends it, is what closes this.
