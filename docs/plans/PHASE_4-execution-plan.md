# LabCairn Phase 4 执行计划

**版本：** 0.1（讨论确定版）  
**阶段：** Phase 4 规划与建设  
**起点：** Phase 3 已收口，退出结论为 `PASS WITH NOTES`  
**首发范围：** Windows 课题组内部使用  
**计划状态：** 可据此拆分工作单，具体任务编号和负责人待开工时登记

## 1. Phase 4 的建设目标

Phase 4 将 Phase 3 已经验证的工程基础建设成课题组可以持续使用的科研工作台。首轮建设围绕论文改稿展开，同时启动多源研究学习的第二条工作线。

Phase 4 的首轮结果应当让一名导师和数名学生能够围绕一篇真实、脱敏、经过授权的论文，完成从导入、模型建议、逐条审批、修改应用到四份交付物导出的完整流程。系统自动记录过程数据，导师和学生补充质量结论，形成下一轮修复依据。

## 2. Phase 3 收口基线

Phase 3 的 G4 退出门已经关闭，最终判断为 `PASS WITH NOTES`。已有能力包括：

- Windows 桌面壳、安装、启动、升级、卸载和运行环境供应。
- 论文导入、版本、意见、修订、审批、事件流和证据展示的基础链路。
- DOCX 修改和关键 OOXML 结构修复。
- WPS Office 与 Word 2019 的双主机重新打开验证。
- 权限边界、拒绝路径、故障演练、诊断记录和操作手册。
- Web 工作台测试 142 项通过，Phase 4 相关 Python 目标测试 60 项通过。

Phase 3 留给 Phase 4 的主要工作包括：

- 完整的 apply 与 publish 交付链路还没有在真实试用中跑通。
- 四份交付物需要在真实流程中绑定到同一任务、输入版本和输出版本。
- 真实模型建议需要在脱敏真实样稿上完成并经过人工审批。
- 取消、重试和恢复需要在完整交付环节中验证。
- 部分意见定位、科研质量判断和权限拒绝类别仍需补齐。
- 当前界面仍以工程验证型面板为主，需要形成统一的产品交互和动态反馈系统。

## 3. 已确认的产品决策

### 3.1 UI 与交互

- 第一主线是论文改稿工作台。
- 首版直接实现可运行界面，边设计边接入现有 API。
- 工作台采用三栏布局。
- 左侧显示文稿结构和意见导航，中间显示当前文稿，右侧显示建议、证据和审批。
- 点击意见可以定位文稿，滚动文稿也会同步切换当前意见。
- 文稿只高亮当前意见对应的内容。
- 首屏显示最近任务、待处理摘要和任务进度，再进入具体工作台。
- 模型建议采用原文与建议改文并列、依据区域同步展示的方式。
- 审批操作在右侧面板和意见下方同时提供。
- 界面采用反馈感较强的产品化风格。
- 任务状态变化和文稿修改过程都使用明显动态反馈。

### 3.2 关键能力与试用

- 第一优先级是应用交付闭环。
- 修改建议必须逐条人工审批。
- 应用修改前必须预览修改数量、影响段落和输出变化摘要。
- 四份交付物必须全部生成，包括标记稿、清洁稿、逐条回复表和质量报告。
- 默认提供完整交付包，也允许单独导出每一份文件。
- 第一轮试用直接接入一款真实模型。
- 真实模型失败时提供重试和切换替身模型两条路径。
- 首轮试用规模为 3—5 人、单课题。
- 参与角色为导师 1 人、学生 2—4 人。
- 材料使用经过授权的真实论文脱敏副本。
- 首轮试用以完成一篇论文的完整改稿闭环作为结束条件。
- 首轮评价同时观察改稿效率、修改质量和可追溯性。
- 系统自动记录操作过程，人工补充质量结论。
- 试用问题同时记录严重程度和问题类型。
- 版本采用核心工作包版本加试用修复版本的节奏。

### 3.3 多源学习

- 多源学习作为 Phase 4 的第二条工作线，在 UI 和改稿闭环形成可运行基线后启动。
- 首批导入顺序为论文与改稿轨迹、PPT、会议音频。
- 原始材料进入 RAG 知识库，经过导师审核的稳定经验再提炼为指导规则。
- 审核后的规则可以供课题组其他项目使用。
- 规则发布由导师单人审核即可完成。
- Agent 使用规则时，界面展示规则名称和简要说明。
- 会议音频首版先使用已有转录或人工整理文本。
- PPT 首版处理文字、备注、表格和图片，并保留来源位置。

## 6. P4-UI 文稿驱动工作台

### 6.1 页面结构

首屏展示最近任务和待处理摘要，包括任务名称、当前阶段、待审批意见数量、最近活动和错误提示。进入任务后采用三栏布局：

- 左栏显示文稿结构、版本选择和意见导航。
- 中栏显示当前文稿内容，当前意见对应段落高亮。
- 右栏显示模型建议、意见依据、证据定位和快速审批。

滚动文稿时同步切换当前意见。点击意见时文稿定位到相应内容。当前阶段只强化一条意见，避免全文同时出现大量高亮。

### 6.2 审阅交互

每条意见需要显示：

- 导师意见原文和定位。
- 原文片段与建议改文的并列对照。
- 建议依据和证据入口。
- 接受、部分接受、拒绝和需要证据四种处理方式。
- 当前处理状态和下一步操作。

右侧面板提供快速操作，意见下方提供完整说明。应用修改之前必须显示影响范围和输出预览。

### 6.3 动态反馈

动态效果覆盖两类场景：

- 任务状态从导入、定位、生成、整理、审批到交付的阶段变化。
- 文稿修改应用时的新增、删除、替换和输出版本变化。

首版采用明显动态。动效必须与状态绑定，不能只做装饰。所有重要状态同时提供文本和结构化状态，避免用户只能依靠颜色或动画判断结果。后续仍应保留降低动态效果的可配置入口。

### 6.4 UI 验收

- 用户可以从最近任务摘要进入指定改稿任务。
- 点击意见可以定位当前段落，滚动文稿可以切换意见。
- 当前意见能够同时展示原文、建议改文、依据和审批操作。
- 导入、分析、模型调用、审批、应用和导出都有阶段反馈。
- 失败状态显示原因，并提供重试或切换替身模型入口。
- 应用修改前能够查看预览，应用后能够看到版本变化。
- 四份交付物在统一交付中心显示状态、版本绑定和导出操作。

## 7. P4-CAP 关键能力补齐

### 7.1 应用与发布闭环

实现并验证以下链路：

1. 导入脱敏论文和导师批注。
2. 解析意见并定位到文稿内容。
3. 调用真实模型生成建议。
4. 用户逐条审批建议。
5. 展示修改预览。
6. 应用批准修改。
7. 发布标记稿和清洁稿。
8. 生成逐条回复表和质量报告。
9. 将四份文件绑定到同一任务、输入版本和输出版本。
10. 生成发布回执和可追溯摘要。

每一步都要保留版本、摘要、权限和操作记录。重复执行不能产生重复交付物或重复发布记录。

### 7.2 真实模型闭环

- 采用一款经过授权的真实模型。
- 真实请求只使用脱敏样稿和允许发送的必要片段。
- 记录模型、请求数、token、耗时、失败、拒绝和停止原因。
- 模型建议必须与导师意见和人工审批结果分开保存。
- 真实模型不可用时支持重试和切换替身模型。
- 替身模型输出不能被误记为真实模型结果。

### 7.3 取消、重试和恢复

补齐完整交付过程中的：

- 用户取消。
- 网络或模型超时。
- 文件被锁定或发生变化。
- 导出中断。
- 重启后恢复已完成阶段。
- 已生成文件的摘要校验。
- 失败步骤的可重试和不可重试说明。

### 7.4 质量与证据

补齐：

- 意见覆盖检查。
- 建议与意见的对应检查。
- 修改范围检查。
- 证据是否补齐检查。
- 回复表与实际修改是否一致。
- 质量报告与四份交付物是否绑定一致。

## 8. P4-MS 多源学习工作线

### 8.1 首批顺序

多源学习在 P4-UI 和 P4-CAP 形成可运行基线后启动，首批材料按以下顺序进入：

1. 论文与改稿轨迹。
2. 汇报 PPT。
3. 会议音频的已有转录或人工整理文本。

论文和改稿轨迹首先用于复用现有的修改逻辑。PPT 接着补充汇报论证、图表、备注和证据位置。会议材料最后补充讨论、问题、判断和后续行动。

### 8.2 双层学习结构

原始材料和经过处理的材料进入 RAG 知识库，保存来源版本和定位信息。经过导师审核、适用范围明确且能够复用的经验，提炼为指导规则。

指导规则必须保存：

- 规则名称和简要说明。
- 适用范围。
- 来源材料指纹和定位。
- 导师审核人和审核时间。
- 规则版本和撤回状态。

Agent 使用规则时，在界面展示规则名称和简要说明。规则内容可以供课题组其他项目调用，原始材料仍按权限边界管理。

### 8.3 PPT 处理范围

首版处理：

- 幻灯片文字和标题。
- 演讲者备注。
- 表格。
- 图片及其所在幻灯片位置。

每个提取结果都要保留 PPT 版本、页码或对象位置和来源指纹。图表无法可靠解析时记录限制，不生成无依据结论。

### 8.4 音频处理范围

首版使用已有转录或人工整理文本，不把自动转录作为第一阶段阻塞条件。后续接入自动转录时，需要增加时间戳、说话人不确定性、术语校对和人工修正记录。

### 8.5 多源学习验收

- 论文修改轨迹可以被检索并指向原始意见和修订位置。
- PPT 的文字、备注、表格和图片可以被检索并指向正确页面或对象。
- 会议整理文本可以被检索并指向原始记录版本。
- Agent 可以检索 RAG 依据并显示规则名称和简要说明。
- 只有导师审核后的经验才能进入课题组共享规则集合。
- 未审核的关系和经验只能作为候选内容，不能直接作为行为准则。
- 规则撤回后，新的任务不再检索到已撤回规则。

## 9. P4-PILOT 真实试用

### 9.1 试用对象和材料

- 一个课题。
- 3—5 名成员。
- 导师 1 人，学生 2—4 人。
- 一篇经过授权的真实论文脱敏副本。
- 保留批注、修订痕迹和论文结构。
- 删除姓名、单位、项目编号和其他不必要的敏感信息。

### 9.2 试用流程

1. 导入论文、批注和修订版本。
2. 检查原始文件摘要和版本信息。
3. 运行真实模型生成建议。
4. 导师和学生查看阶段进度。
5. 逐条查看意见和建议依据。
6. 预览修改影响。
7. 逐条审批建议。
8. 应用批准修改。
9. 生成标记稿、清洁稿、逐条回复表和质量报告。
10. 在统一交付中心导出完整交付包，并按需单独导出文件。
11. 由系统保存过程记录。
12. 由导师和学生补充质量结论。

### 9.3 试用评价

试用评价同时观察效率、质量和可追溯性：

- 完成一篇论文所需时间。
- 人工补做步骤数量。
- 建议接受、部分接受、拒绝和补证据数量。
- 意见覆盖率。
- 意见与修改的对应正确性。
- 证据定位正确性。
- 四份交付物的一致性。
- 用户发现的阻断和严重问题。

不把长期使用意愿作为验收指标。课题组本身就是持续使用场景，首轮试用的任务是发现缺陷、修复缺陷并提高日常工作质量。

### 9.4 问题记录

问题记录采用系统内记录加统一反馈表：

- 系统内记录任务、版本、意见、操作步骤、错误、耗时和重试信息。
- 统一反馈表记录主观体验、问题描述和改进建议。
- 每个问题同时标记严重程度和问题类型。
- 严重程度包括阻断、严重、一般和建议。
- 问题类型包括功能、界面、性能、模型和文档。

## 10. 版本和发布节奏

Phase 4 采用两类版本：

- 核心工作包版本。完成 UI 基线、交付闭环或多源学习等核心工作后发布，作为可回退的稳定节点。
- 试用修复版本。根据真实试用问题持续发布，记录修复项、回归结果和已知限制。

每个版本至少记录：

- 版本号和源代码提交。
- 安装包摘要。
- 数据和 API 兼容性。
- 新增能力。
- 修复问题。
- 未关闭限制。
- 回滚方式。
